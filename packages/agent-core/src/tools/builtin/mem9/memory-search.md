Search mem9 long-term memory for durable facts and prior knowledge across sessions.

Use this tool before answering questions that depend on historical context, prior decisions, stored notes, project or team facts, domain knowledge, environment details, workflows, conventions, recurring problems, lessons, or other stable context that may not be present in the current session.

You MUST call this tool before asking the user to repeat stable context that could be in long-term memory. Search first and wait for the result; only ask the user if no relevant memory is found after at least two rephrased queries. This applies to missing facts, referents without antecedents, pronouns or demonstratives whose meaning depends on prior interaction, previously stored decisions, conventions, workflows, project state, domain notes, or environment details.

Use a short query close to how stored facts are worded, not the user's full utterance. Prefer concrete content words from the user's request, likely stored predicates, and known entity names over abstract labels or synonyms. Good queries: "project deadline", "team coding conventions", "deployment workflow", "customer staging environment", "user lives in", "where user lives". Bad queries: "tell me about the user's project", "user home location", "user residence", "my home".

Do not use this tool to search the current repository; use Grep or Read instead. Do not use it for trivial greetings, one-off task instructions, or information already visible in the current conversation.

If the result includes a retry hint or no relevant memory is found, follow it and try at least two rephrased queries before giving up. Vary both predicate wording and key terms, such as "lives in", project names, team names, locations, deadlines, tools, or environment names. A good retry strategy is: first include the user's content word or referent category, then try a complete predicate phrase with prepositions, then combine them, for example "home" -> "user lives in" -> "where user lives in".

When retrying, change the ENTITY or OBJECT words, not just the verb: a broad query like "user research" repeated with synonyms ("user researched", "user studied") will keep returning the same near-matches. Pull a concrete object into the query instead — what was researched, where, with whom (e.g. "user research" -> "user researching adoption agencies"). If a result you need may exist but the shown candidates are low-confidence, re-search with a higher `limit` (the header "Showing top N of M candidates" tells you when M exceeds what you saw); entries you have not seen may rank just below the cutoff.

When a question asks for multiple items — activities, plans, examples, "what things", "which ones" — do not stop after the first satisfying result: memories covering different facets of the same topic rank differently per query, so one search rarely surfaces them all. Run several targeted searches that vary the facet (different activities, objects, places, companions, or time periods), keep going until a new search stops surfacing new items, and combine every distinct item your memories support into the answer.
